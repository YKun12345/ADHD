# 小程序医生工作台设计

## 目标与范围

在现有患者微信小程序中加入研究者/医生移动工作台，复用 FastAPI 已有研究者接口。首期包含研究者登录、角色分流、仪表盘、绑定患者、已绑定患者列表、患者综合报告、医患消息查看与发送。

不在首期加入影像文件上传、脑影像可视化、模型推理、DAC 安全管理和研究数据库管理。这些操作继续在电脑医生端完成。

## 方案选择

采用同一小程序内的双角色工作台，而不是 WebView 嵌入医生网页或另建第二个小程序。原因是可以复用请求层和设计系统，同时保留后端角色校验和患者归属校验。

## 角色会话

- 登录页提供“患者”和“医生/研究者”两个明确选项，默认患者。
- 登录请求分别发送 `role: patient` 或 `role: researcher`。
- 登录响应中的实际角色必须与选择一致，否则不保存 token。
- 患者进入 `/pages/home/index`，研究者进入 `/pages/doctor-home/index`。
- 患者页面继续使用现有患者守卫；医生页面使用独立研究者守卫。
- 切换角色或退出时清理 token、用户资料和患者端本地草稿，防止跨角色残留。
- 医生查看的患者报告与消息只保存在当前页面内存，不写入微信本地缓存。

## 医生工作台

医生首页请求：

- `GET /doctor/dashboard_stats`
- `GET /doctor/my_patients`
- `POST /doctor/bind_patient`，请求体 `{ patient_email }`

页面显示患者总数、本周报告数、待影像数量，以及已绑定患者的类型、最新量表风险、认知完成数、追踪天数和下一步提示。点击患者进入详情页。

## 患者详情

详情页通过查询参数接收整数 `patient_id`，非法或缺失参数不发送请求并返回工作台。页面请求：

- `GET /doctor/patient/{patient_id}/report`
- `GET /care/doctor/patient/{patient_id}/messages`
- `POST /care/doctor/patient/{patient_id}/messages`，请求体 `{ content }`

页面展示量表摘要、七项认知指标、追踪摘要、关怀建议、模型/影像是否存在和消息列表。消息必须去除首尾空白，长度限制 1–2000 字；发送按钮在请求期间禁用。

## 安全与错误处理

- 不能仅依靠前端隐藏页面；后端现有 `require_roles(RESEARCHER)` 和患者归属检查继续作为安全边界。
- 401 继续由统一请求层清除会话并回登录页。
- 404 患者归属失败只显示统一提示，不泄露其他患者是否存在。
- 绑定患者和发送消息必须由医生主动点击触发。
- 页面不显示内部数据库 ID 之外的额外敏感字段，不缓存完整报告，不加入调试日志。
- 所有内容继续标注为辅助筛查与随访信息，不替代医生诊断。

## 视觉设计

医生工作台使用雾蓝、靛青与少量暖橙作为独立主题，与患者端柔和多彩背景明显区分。卡片保持现有大触控区域、清晰层级和低干扰风格。

## 验证

- 角色会话、登录分流、非法角色和跨角色清理单元测试。
- 医生页面控制器测试覆盖加载、绑定、报告、消息发送和失败状态。
- 页面结构测试覆盖 API 路径、无障碍标签、敏感缓存禁令和角色守卫。
- 小程序完整测试、JavaScript 语法、JSON 解析与 Git 差异检查。
- 不在自动测试中真实绑定患者或发送消息。
