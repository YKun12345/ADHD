# 后端发布前硬化设计

## 1. 背景与目标

两份任务 PDF 确定的产品主线是“微信小程序患者端 + FastAPI 后端 + 医生 Web”双轨演示。当前仓库已经覆盖登录注册、量表、七类认知任务、14 天追踪、综合报告、AI 页面、医生端、上传与模型 Mock/真实推理边界，因此本轮不重复建设页面，而是处理会削弱联调和交付可信度的缺陷。

本轮目标是让后端在存在本地 `backend/.env` 时仍能正确尊重测试、命令行和部署环境变量，修复已注册 API 路径中的确定性运行时错误，减少框架弃用告警，并建立可重复的自动化验收证据。

## 2. 方案选择

### 方案 A：继续扩充患者端页面

优点是视觉成果明显；缺点是 PDF 的主要页面已完成，不能解决当前 15 项后端测试失败和接口运行时风险。

### 方案 B：全仓大规模重构

优点是可一次清理更多历史代码；缺点是范围跨越小程序、医生端、模型和大量实验性 AI 服务，会给当前演示分支引入不必要风险。

### 方案 C：发布前硬化（采用）

聚焦配置优先级、测试隔离、真实运行时错误、框架生命周期和静态检查。该方案直接服务于 B 的“后端稳定 + 联调”职责，同时保护 A 已完成的小程序行为不变。

## 3. 架构与边界

- 配置层：`backend/.env` 只补充进程中未提供的变量。操作系统、测试夹具和部署平台显式设置的变量拥有更高优先级。
- 应用生命周期：数据库初始化由 FastAPI `lifespan` 管理，保持启动时建表/升级行为不变，移除弃用的 `on_event` 注册。
- Schema：使用 Pydantic v2 `ConfigDict` 表达 ORM 属性读取能力，响应字段和接口契约不变。
- AI 服务：提醒生成必须使用专用 `REMINDER_SYSTEM_PROMPT`；自然语言查询所需模型在模块作用域显式导入，避免局部导入造成运行时 `NameError`。
- 静态质量：修复 Ruff 报告的未定义名称、重复字典键、无效比较、无占位 f-string、无用导入/变量和 lambda 赋值。不得借机改变业务输出。
- 工作区保护：不覆盖用户已修改的 `miniprogram/project.config.json`，也不改动 A 端既有行为。

## 4. 数据流与错误处理

启动时先读取 `backend/.env` 中尚未由进程提供的默认值，再构建 `Settings`、数据库引擎和 FastAPI 应用。测试夹具设置临时 SQLite 路径后重新导入应用，必须始终落到该临时数据库；生产环境显式设置 `APP_ENV=production` 时，缺失数据库地址或使用占位密钥必须在导入配置时立即失败。

AI 提醒的提供商调用成功时返回提供商结果；只有真实的提供商异常才进入现有模板降级。自然语言查询必须在有患者数据时完成查询，不得把内部 `NameError` 包装成“无法理解查询”。

## 5. 测试与验收

1. 先保留并复现现有后端测试失败，证明 `.env` 覆盖问题存在。
2. 新增 AI 提醒和自然语言患者查询的回归测试，并确认修复前按预期失败。
3. 新增弃用回归测试，确认导入应用不再触发 `on_event` 和 Pydantic class Config 告警。
4. 逐项修复后运行后端完整测试、小程序 77 项测试、仓库审计、Python 编译和 Ruff 全量检查。
5. 更新验证证据，明确自动化已覆盖范围与仍需微信开发者工具、真机、真实 MySQL、真实 HGST 权重和医学合规人员完成的外部验收。

## 6. 非目标

- 不宣称医学有效性、临床可用性或生产合规。
- 不替用户注册 AppID、配置域名/证书、提供真实模型权重或执行真机验收。
- 不重做已完成的小程序 UI、七类认知任务或医生端页面。
- 不修改真实密钥、患者资料或用户本地配置。
