# A+B 项目任务与进度总表设计

## 1. 目的

建立一个由 A 和 B 共同使用的单一 Markdown 项目总表，完整记录两人的任务、详细步骤、依赖关系、验收标准、最终交付物、当前进度、阻塞事项和更新历史。

该总表用于回答四个问题：

1. A 和 B 分别应该做什么；
2. 每项工作怎样才算真正完成；
3. 当前项目实际完成到哪里；
4. 为完成比赛演示和最终交付，下一步应该做什么。

- `C:\Users\Lenovo\Desktop\202605010110-----参赛作品总文件夹\adhd智慧辅助诊断平台.pdf`

当前完成状态以工作区文件、可运行结果、接口测试、真机结果和 A/B 的明确进度反馈为依据。文件存在但未运行验证时，只能记为“待验证”，不能记为“已完成”。

采用单文件方案，避免 A、B 和总进度分别记录后互相不一致。Git 仓库建立后，该文件与项目代码一起同步。

## 4. 总表结构

总表固定包含以下部分：

1. 项目信息：项目名称、目标、比赛日期、当前阶段、最后更新时间；
2. 进度总览：A、B、共同任务和最终交付物的分项进度；
3. 状态与证据规则：统一状态、完成度和验收口径；
4. A 的完整任务：基础设施、登录、首页、量表、认知测试、追踪、报告、AI、科普、真机和演示资产；
5. B 的完整任务：Git、后端、数据库、鉴权、业务接口、医生 Web、模型模拟、上传、部署、数据、文档和作品报告；
6. A+B 共同任务：AppID、代码同步、接口契约、每日联调、全链路验证和最终彩排；
7. D1-D18 排期：按两份 PDF 中的 18 个工作日计划记录负责人、目标和完成状态；
8. 最终交付物：小程序、后端 API、医生 Web、演示数据、二维码、视频、PPT、报告 PDF、API 文档和源码包；
9. 阻塞与决策：记录影响进度的问题、负责人、解决方案和截止时间；
10. 实时更新日志：记录每次状态变化的时间、人员、证据、变化内容和下一步。

## 5. 任务字段

每项任务使用同一组字段：

| 字段 | 含义 |
| --- | --- |
| ID | 稳定编号，例如 A-01、B-01、AB-01 |
| 阶段 | D1-D18 或缓冲期 |
| 任务 | 可交付的工作名称 |
| 详细步骤 | 完成任务所需的具体操作 |
| 依赖 | 开始或完成前必须具备的条件 |
| 验收标准 | 可观察、可验证的完成证据 |
| 状态 | 当前统一状态 |
| 完成度 | 0%、25%、50%、75% 或 100% |
| 最后更新 | 最近一次发生实际变化的时间 |
| 下一步 | 当前最小可执行动作 |

## 6. 状态与完成度

统一使用以下状态：

- `⬜ 未开始`：尚未产生有效工作成果；
- `🟡 进行中`：已经开始，但未达到验收标准；
- `🔵 待联调`：单方功能基本完成，需要另一方接口或联合验证；
- `🟣 待验证`：已有代码或文件，但没有可靠运行证据；
- `🟢 已完成`：全部验收标准均有证据；
- `🔴 阻塞`：存在明确依赖问题，当前无法继续。

完成度只使用五档：

- 0%：未开始；
- 25%：已准备或已搭建骨架；
- 50%：主要功能已经实现，但尚未完整；
- 75%：功能基本完成，等待联调或最终验证；
- 100%：已通过全部验收标准。

总体进度分别统计 A、B、共同任务和最终交付物。每个分项的进度为该分项所有任务完成度的算术平均值，不用某一方已有的大量代码掩盖另一方尚未开始的关键任务。

## 7. A 的职责边界

A 主责 `miniprogram/` 全部内容以及移动端演示资产，主要交付包括：

- 原生微信小程序基础结构、全局样式和页面路由；
- 基于 `wx.request` 的请求封装、token 存储和认证拦截；
- 账号密码登录注册，不使用模板中的 `wx.login` 作为业务登录；
- 患者首页和 14 天任务进度；
- ASRS 18 题、SNAP-IV 26 题的移动端量表页面；
- 自写 Go/No-Go 与 Stroop 触摸反应测试；
- 14 天追踪页面、模拟数据入口和折线图；
- 综合报告、五维雷达图和趋势图；
- AI 助手聊天、临床路径和科普页面；
- iOS/Android 真机测试、演示视频、答辩 PPT 和现场小程序二维码。

A 的最终核心交付物是：可扫码运行并完成患者闭环的小程序、演示视频和答辩 PPT。

## 8. B 的职责边界

B 主责 Git 仓库、`backend/`、医生 Web、服务部署和后端交付资料，主要交付包括：

- 建立私有 Git 远程仓库、合理的 `.gitignore`、主分支与同步规则；
- FastAPI、MySQL/数据库表、JWT、注册登录和 CORS；
- 量表提交与算分、认知测试存储、14 天追踪和综合报告接口；
- AI 聊天、文件上传及类型校验、模拟预测接口；
- 医生端患者列表、统计、患者报告、影像上传和预测结果联调；
- 一名成人和一名儿童的演示数据以及 `.1D` 样例；
- 局域网热点或内网穿透部署、API 文档、源码包和作品报告 PDF。

B 的最终核心交付物是：稳定可访问的后端 API、可演示的医生 Web、演示数据、API 文档和作品报告。

## 9. 共同职责

A 和 B 共同负责：

- 使用同一 AppID 并配置开发者、体验成员权限；
- 每天开始前拉取代码，结束前提交并推送；
- 明确接口字段、状态码、错误信息和认证方式；
- 每天安排固定联调时间；
- 使用手机通过局域网 IP 或临时公网地址访问 B 的后端；
- D14 前跑通患者端完整链路；
- D18 完成患者小程序与医生 Web 的联合彩排；
- 比赛当天准备体验二维码、测试机和录屏兜底。

## 10. 初始状态录入规则

根据 2026-08-20 的实际工作区和用户反馈，首次总表按以下原则录入：

- A 的小程序账号、AppID、开发者工具、项目骨架、登录页静态标题和基础样式记为已完成或部分完成；
- A 的真实账号密码登录、请求封装、首页业务、量表、认知测试、追踪、报告、AI 和科普功能记为未开始；
- B 已安装微信开发者工具、已获得开发者权限，记为环境准备部分完成；
- 根目录没有 `.git`，Git 仓库任务记为未开始；
- 工作区已有 FastAPI、数据库模型、接口和医生 Web 文件，但未取得本轮运行验证证据，相关任务记为待验证；
- AppID 协作记为部分完成，Git 同步和 API 联调记为未开始。

## 11. 更新流程

“实时更新”定义为事件驱动更新：每当 Codex 完成并验证一项工作，或 A/B 明确报告并提供可核实进度时，立即更新同一个总表。

每次更新执行以下动作：

1. 更新对应任务的状态、完成度、证据、最后更新时间和下一步；
2. 重新计算 A、B、共同任务和最终交付物的分项进度；
3. 更新阻塞与决策记录；
4. 在更新日志追加一条记录，不覆盖旧记录；
5. Git 建立后，由修改者先拉取再修改，完成后提交并推送。

本地 Markdown 文件不会自行监控 A、B 的电脑或开发工具。未报告、未同步、未验证的工作不得自动推定完成。

## 12. 冲突与异常处理

- A、B 同时修改进度文件时，以 Git 合并后的事实为准；冲突必须人工核对，不直接覆盖任一方记录；
- 任务超期时保留原排期，同时把下一步移入当前日期，不伪造完成日期；
- 接口、真机或演示验证失败时，将任务从“已完成”退回“进行中”或“阻塞”，并记录原因；
- PDF 计划与当前项目实现冲突时，保留计划要求，并在决策区记录最终采用的实现方式；
- 医疗相关输出统一注明“仅用于辅助筛查，不替代专业医生诊断”。

## 13. 验证要求

总表建立后必须完成以下检查：

1. A、B、共同任务和最终交付物均有独立清单；
2. 两份 PDF 中明确出现的核心任务没有遗漏；
3. 当前项目状态与实际文件、Git 状态和用户反馈一致；
4. 每个任务都有可执行的下一步和可观察的验收标准；
5. 没有把“文件存在”误判为“功能完成”；
6. 更新日志包含首次建表记录；
7. Markdown 表格、复选框和路径可正常阅读。
